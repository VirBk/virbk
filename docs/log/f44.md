# F44 — the census counts seats, not the processes one launch spawns (correction 1)

## What changed

`factory/tools/seat.mjs` and this file. The fold the review cleared and the
ancestor walk are untouched, and the two cleared probes still hold: a self-parent
row resolves to one seat without looping, and two independent launches with
interleaved pids stay separate. One change per dictated item.

**Item 1 — the walk never erases a seat.** Windows stamps `ParentProcessId` at
creation and never clears it when the parent dies, and `Get-CimInstance` does not
enumerate atomically, so pid-reuse churn can leave two counted rows that are each
other's parent. The old walk returned the row itself on a revisit, and because it
tested `counted` before it tested the walk, the two rows folded into *each other*
and both vanished — `0 running writer seat(s)` while seats exist. That is worse
than the over-count this lane fixes: the two-writer ceiling and the dead-seat
resume read this number. `seatOf` now collects the traversal path and the first
counted ancestor seen; when the walk returns to a pid it has already walked it has
found a cycle, cannot pick a nearest ancestor, and the seat is the counted row with
the **LOWEST pid in the cycle**. Deterministic, and no row is erased.

**Item 2 — a torn chain is reported, not silently counted as another seat.** A
counted row whose own `ParentProcessId` is in no row cannot be attached to its
launch: the parent exited between the enumeration and the write. The gap cannot be
inferred, so the row is still **counted**, the census names the row and the pid it
could not reach, and the summary says how many rows have a broken chain and that
the count may over-report. An honest number with its uncertainty named beats a
confident wrong one.

**Item 3 — no uncommanded count.** The sentence "Before this change the same
machine printed `3 running writer seat(s)`" is **deleted**. No command produced
that 3. The measured number for this machine is below, with its command.

# F43 — a print-mode recipe names its approval mode

Envelope F43. Base `cafac16`. Holds: this file and `factory/tools/seat.mjs`.

## What the lane found

Sitting 11 launched two seats from the `qwen-code` recipe exactly as written. Both
read their packet, did the analysis, wrote nothing, and said so only because they
thought to. The carrier line was `qwen --auth-type openai --model <id> -p -` —
print mode, so no terminal, while `--approval-mode` defaults to `default`, which the
help spells as "Require approval for file edits or shell commands". Every edit and
every command waited on an approval nobody was there to give. The recipe named the
right harness and the wrong mode, and nothing in the file could say so (T07: a
recipe remembered, not read).

## `factory/tools/seat.mjs`

`git hash-object` before the lane `d9a1d0cdbe4b954ee3a617f95bfc1c2a2765c363`,
after `2d4c18fafb4c24af0302595aa522e79f486b1912`.

The option is read off a help output run on this machine, never remembered:

```text
$ qwen --help
      --approval-mode   Set the approval mode: plan (Analyze only, do not modify files or execute commands), default (Require approval for file edits or shell commands), auto-edit (Automatically approve file edits), auto (LLM classifier auto-approves safe actions, blocks risky ones), yolo (Automatically approve all tools)  [string] [choices: "plan", "default", "auto-edit", "auto", "yolo"]
  -y, --yolo            Automatically accept all actions (aka YOLO mode, ...)?  [boolean] [default: false]
```

Long form `--approval-mode yolo`. A `-y`/`--yolo` shorthand also exists; the long
form is the one whose choices a reader can check against the help text.

1. **`qwen-code`** — the carrier now reads
   `qwen --auth-type openai --model <id> --approval-mode yolo -p -`, with the
   help-read note above it. `-p -` is untouched, so the packet still arrives on
   stdin (T72). `desktop-qwen` is an alias of this recipe and moves with it.
2. **aider, opencode, goose** — none is installed here, so no option was invented.
   Each says so in one line drawn from a single constant, so the recipe and the
   check that reads it cannot drift apart:
   `A print-mode launch needs the harness's own auto-approve option. UNVERIFIED here: confirm it from that harness's own help output before launching.`
3. **The rest of the rendered carriers**, because the work sentence is "every seat
   recipe" and the failure is a property of print mode, not of one harness:
   `local-hands`, `cloud-grok`, `cloud-git-bus`, `pc-token` take the note;
   `pc-dashscope` and `cloud-dashscope` take `--approval-mode yolo` — they are the
   same qwen carrier with a model interpolated. Nine carriers, plus goose's note.

## The check

`--self-test` renders every recipe, reads the **rendered** text, finds each recipe's
stdin carrier the way that recipe prints it, and collects the ids whose carrier names
no approval option and whose recipe does not carry the note. One assertion:

    a print-mode carrier names no approval mode   (ids follow on failure)

Sweep: the 10 of 19 recipes whose block prints a `< packet.txt` line. A recipe with
no stdin carrier is not a print-mode launch line and has no mode to state. A guard
asserts the carrier set is non-empty, so a refactor that stops rendering carriers
fails rather than passes vacuously (T09/T13).

**Named gap.** `goose` prints no carrier line, so the check cannot read it. Item 2
still required its note and it carries one; the check is blind to that one recipe.

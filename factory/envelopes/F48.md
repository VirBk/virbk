What you cannot see from the file
  pathCitations() treats every backticked token with a slash, no whitespace, no glob character and a source extension as a path into this tree. Two kinds of token are not that.
  A revision spec, HEAD colon factory/tools/packet.mjs, resolves — git rev-parse prints its blob — and rule H rejected one at F45's landing, on a record whose claim was true. That is S25, and it is what this lane is booked for.
  A URL is extracted today too. Found at the objects when this envelope was written, not booked from a spark, and it is the same defect: the extractor never asks what kind of token it has.

The rule to implement
  Split a token holding a colon at its FIRST colon. If the remainder begins with two slashes the token is a URL: not a path citation, not checked. Otherwise it is a revision spec — left side rev, right side path — and rule H checks THE PATH PART against the tree. A token with no colon is a tree path, checked exactly as today.
  Do NOT resolve the rev with git. Rule H runs inside the gate from an unpacked archive that is not a repository; files() already falls back to a directory walk when git ls-files fails there. A check that shelled out to git rev-parse would pass on the control plane's disk and could not run where the gate runs. The path part carries all the evidence this rule needs: an invented HEAD colon factory/nope.mjs still names a file that is not in the tree.

  2 A rev spec whose path part is NOT in the tree still fails, and the message names the path part, not the whole token. This is the member most likely to escape a rule written as "accept rev specs".
